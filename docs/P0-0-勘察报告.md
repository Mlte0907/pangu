# P0-0 勘察报告：存储路径分叉（v1/v2）导致高级模块集体空转

> **本文件是勘察报告，不含任何代码改动建议的实施。**
> 所有数据来自 2026-09-14 本机实测。标注 ❓ 的是尚未确证的点。
> 目的：先摸清情况，再决定怎么修。

---

## 一、结论摘要

盘古有 **132 个** `pangu/memory/` 模块，但生产服务实际加载 **15 个**。
调查发现根因**不是"模块没实现"**，而是：

> **记忆数据存在两套路径，19 个文件里只有 2 个知道新路径（v2）的存在。
> 其余读的是空的旧路径（v1）。**

后果：所有依赖"读取记忆列表"的高级功能，**输入恒为空，输出恒为空，且静默不报错**。

## 三、为什么这是"静默"故障

三个叠加因素让它隐藏了 81 次调度：

1. **`_load_drawers()` 读不到就 `return []`**：
   `autonomous.py:116-118`
   ```python
   def _load_drawers(self) -> list[Drawer]:
       if not self._drawers_file.exists():
           return []
   ```
   文件**存在但是空的**（`[]`），所以走的是 `json.load` 成功的分支 → 返回 `[]`。
   **没有任何"数据源为空"的告警。**

2. **任务"成功"**：对空列表执行 dedup/decay/dream 都返回
   `{"status":"completed", stats:{全 0}}` —— 技术上确实没出错。

3. **`except: pass` 包裹**：`memory_ops.py:47-52` 的
   `on_memory_written()` 调用被 `try/except: pass` 包着，
   任何异常都被吞掉。

## 四、闭环：写入 → 触发维护 → 空转

这是完整的失效链路（已端到端实测）：

```
1. AI 调 pangu_add_memory
   └→ pangu/server/handlers/memory_ops.py:48
      server.memory.add_drawer(drawer)          ← 写入 v2 ✅ 正确
      on_memory_written()                        ← 计数 +1

2. on_memory_written()（autonomous.py）
   _write_counter += 1
   if _write_counter >= 10:                      ← 阈值实测 = 10
       engine.run_cycle()                        ← 触发维护

3. run_cycle() → _load_drawers()
   读 ~/.pangu/palace/drawers.json → []           ← ❌ 空
   → 对空列表跑 fusion/compression/decay/...

实测证据：
  _WRITE_HOOK_THRESHOLD = 10
  调度器读的文件        = /home/xiaoxin/.pangu/palace/drawers.json
  读到的条数            = 0
  tick() = {'total_memories': 0, 'should_run': True,
            'pending_tasks': ['fusion','compression','decay',
                              'vector_rebuild','collect']}
```

⇒ **每写 10 条记忆，就白白触发一次对空集的维护。**

## 六、核实结果（勘察后补：原 5 项任务已完成）

### ✅ 任务 2：`drawer_storage.py` **不是**问题所在

`:400` 位于工厂方法 `DrawerStorage.create(palace_path, ...)`——
路径由**调用方传入**，该工厂本身不拼死路径。
且 `DrawerStorage.create()` 在生产代码中**无人调用**（备用/遗留接口）。

真正的消费者是 `layers.py:315-320`，它同样**接受 `config.palace_path`**：
```python
db_path = Path(self.config.palace_path) / "drawers.db"      # sqlite 分支
self._storage = JsonDrawerStorage(str(self._drawers_file))   # json 分支
```
⇒ **`layers.py` 本身是干净的**。它读什么，取决于**调用者传了什么 config**。

**这个发现把问题定性从"19 个文件各自拼错路径"升级为更本质的一句话：
问题在 `MemoryStack` 的 42 个调用点里，只有 2 个传了正确的 v2 config。**

### ✅ 任务 3：`routes_memory.py` 的 2 处确认

```
:303   drawers_file = _Path(config.palace_path) / "drawers.json"
:380   drawers_file = Path(config.palace_path) / "drawers.json"
```
均在 API 路由内，与 `:370/:379` 的 `MemoryStack(config)` 同源——
**API 侧部分路由也在读 v1**。但注意 `api/server.py:589` 的
`_build_memory_store()` 是正确的，两者并存。

### ⚠【新增，比原判断更严重】`MemoryStack` 调用点普查

全仓 `MemoryStack(...)` 共 **42 处**，只有 **2 处**传 v2 config：

| 位置 | config | 结果 |
|---|---|---|
| `api/server.py:589` | `v2_cfg`（override palace_path → v2_memories） | ✅ 正确 |
| `mcp_server.py:83` | `v2_cfg` + v1 只读合并 | ✅ 正确 |

## 六.5 修正后的根因表述

原表述："19 个文件各自拼错了路径。"

**修正为**：

> `layers.py` / `MemoryStack` 的设计是**正确的**——它接受传入的 config。
> `api/server.py` 与 `mcp_server.py` 也**正确地**构造了指向 v2 的 config。
> **但 `MemoryStack` 的 42 个调用点中，40 个传的是默认 config（指向 v1）。**
>
> 即：**没有任何一处"写错"，而是"该传 v2 的地方没传"**——
> 属于**遗漏**而非**错误**，这也解释了为什么它能长期潜伏：
> 代码本身每一步都"看起来对"。

## 七、修复方向（**仅为方向，未定案**）

### 方案 A：单一权威入口（较彻底）
- 在 config 上加 `authoritative_drawers_path` 一类属性，
  由它统一解析 v2 优先、v1 兜底；
- 40 处全部改为调用它；
- 优点：根治，未来不会再分叉；
- 风险：40 处改动，`lifecycle.py` 一个文件 12 处，回归面大。

### 方案 B：沿用既有兼容模式（较稳）
- 照抄 `mcp_server.py:69-83` 的 F3 做法：把 v1 作为**只读合并源**注入；
- 优点：与已验证的修法一致，风险低；
- 风险：兼容层会长期存在，v1/v2 双轨不清。

### 方案 C：迁移收尾（最干净）
- 把 v1 残留数据合并进 v2，然后**彻底废弃 v1 路径**，
  所有模块只认 v2；
- 优点：终局清晰；
- 风险：需要确认 v1 是否还有其它数据（如 `knowledge_graph.db` 就在 v1 且**是活跃的**）
  → **不能简单废弃 v1 目录，只能废弃 v1 的 drawers 路径**。

### 无论选哪个，必须配套
1. **回归测试**：断言"调度器看到的记忆数 == API 看到的记忆数"
   （这条测试若早存在，81 次空转一次都跑不掉）；
2. **空数据源告警**：`_load_drawers()` 返回空时应 `logger.warning`，
   杜绝同类静默失败；
3. **差分验证**：修复后重跑第四节那个闭环，确认维护任务真的拿到 64 条。

## 9.1 差分实验（原第六节任务 4：**已完成**）

隔离假 HOME 下做对照，证明"v1 文件内容单独决定 `MemoryStack` 读到的条数"：

| 条件 | `MemoryStack().status()['total_drawers']` |
|---|---|
| v1 = `[]` | **0** |
| 把 v2 的 66 条复制进 v1 | **66** |

因果链 **0 → 66** 成立。这是 P0-0 的核心证明物。

⚠️ 假 HOME 实验有一个**致命坑**（本报告先前未记录）：
`~/.pangu/config.json` 里 `base_dir` / `db_path` / `palace_path` 是**绝对路径**，
若不删掉这三个键，假 HOME 会被直接绕过、仍读生产库。
正确做法：只保留 `base_dir = $FAKE/.pangu`，让 `model_post_init` 派生其余路径。

## 9.2 修正：调用点不是 40 处，是 **49 处**

先前报告第五节的"40 处"是**陈旧数字**。实测（当场重跑）：

## 9.3 `pangu stats` 崩溃的精确归因（修正）

第六节说 `total_drawers` 也报错 —— **不准确**。实测 `MemoryStack.status()` 里
`total_drawers` 是**顶层键**，访问它不报错。唯一漂移是 `L0_identity`：

- 代码：`pangu/cli.py:329` 访问 `['memory']['L0_identity']['tokens']`
- 实际：`L0_identity` 嵌在 `layers` 子字典下
- 正确写法：`['memory']['layers']['L0_identity']['tokens']`

## 9.4 U2：默认 28 工具中**受污染的是哪些**（方法学修正）

**先修正一处方法论错误**（队长与调查员都犯过）：最初用"handler 文件是否
传递性 import 了某模块"来判断，得出 5/6 命中 —— **全是假阳性**。
反例：`handlers/search.py` 传递性触达 `fuxi_bridge` / `proactive_reminder` /
`self_repair`，但那些 import 服务于 `pangu_health_report` / `pangu_user_behavior`
等**根本不在默认白名单**的工具。

✅ 正确方法（两步）：
1. 以 `pangu/server/module_registry.py:64` 的 `CORE_WHITELIST`（实测 **28 个**）
   为"是否默认暴露"的**单一事实源**；用 `HANDLERS[tool]` 取实际绑定的函数对象，
   用 AST **只扫该 handler 函数体自身**（不递归整个文件）。
2. 假 HOME 起 `create_app()`，实际调用工具后追踪调用链。

按此方法，默认 28 工具中**确定受污染的有三条路径**：

| # | 工具 | 链路 | 后果 |
|---|---|---|---|
| 1 | `pangu_collect_file` / `pangu_collect_dir` | `collector.py:230-238` `_load_existing()` 读 v1 | **采集去重基线恒为 0** ⇒ 重复采集已存在的记忆 |
| 2 | `pangu_add_memory`（第 10 次调用） | `memory_ops.py:47` `on_memory_written()` → `autonomous.py:535` `get_autonomous_engine()`（无 config 入参）→ `autonomous.py:488` `run_cycle()` 末尾**无条件回写 v1** | 以 0 条为基线回写 |
| 3 | `pangu_search_stats` | — | **不受影响**（`retrieval.py:47-54` 只读内存字典 `_search_stats`，零路径访问） |

实测证据（假 HOME，v1=0 / v2=7）：
`get_collector(cfg)._load_existing()` → **0 条**（修复后 → **7 条**）。

## 9.5 U3：`routes_memory.py` 的两处是**真实 HTTP 路由**

- `server.py:651-653` `include_router(mem_router, prefix="/api/v2")`
- `:303` = `GET /api/v2/memories/search` —— **无鉴权依赖，匿名可打**
  （线上实测 `HTTP 200`）
- `:380` = `GET /api/v2/memories/stats`

**缺陷的活体形态（生产环境实测，两条 curl 即可复现）**：
同一端口 19529、同一 v2 库、同一时刻：

## 9.7 U1：v1 为何变成 `[]` —— **归因修正**

先前判断"是我的清理操作"**过于简化**。逐条验证后的事实：

```
04:02:02  drawers-before-testcleanup-...40202.json   896979 B  119 条
04:02:11  drawers-before-testcleanup-...40211.json   896979 B  119 条
04:03:01  palace-drawers-...40301.json               402 B     1 条（fb_min）
04:03     ~/.pangu/palace/drawers.json → "[]"
04:04:04  commit 0cd5ded「fix(test): 测试套件不再写入生产数据库」
```

`autonomous_state.json` 各任务 `last_run` 均 ≤ `2026-09-14 02:14:09`（**早于 04:03**）
⇒ 调度器当时没运行。而 `0cd5ded` 的提交信息自述
「跑 `pytest` 会直接写入真实库…本轮全量测试期间 69 → 118」。

⇒ **归因应为"清理 + 修复测试隔离漏洞的一次性连续动作"**，

`PANGU_DB_PATH` 时 `palace_path` 仍指向真实 `~/.pangu/palace`。

**【已穷举反证·确证】不存在任何"运行时自动把 drawers.json 写成 `[]`"的代码路径。**
全仓 15 个 `drawers.json` 写点，所有自动入口（`LifecycleManager` 9 个方法 × 2 场景、

**【未能确证】** `04:03` 那一刻的**单条具体命令** —— 无写盘审计日志、mtime 仅到秒。
此边界接受，不再追查。

## 9.8 🔴 新增：`_save_drawers()` 的"空写保护"是**失效**的（真实数据丢失向量）

`layers.py` 原守卫条件：

```python
missing = self._primary_ids - disk_ids
if missing and len(disk_data) >= len(primary_drawers):   # 跳过保存
```

内存为空时 `_primary_ids` **也是空集** ⇒ `missing` 为空 ⇒ **守卫恒不触发** ⇒ 直接覆写。
底层 `JsonDrawerStorage.save()` 更是**无条件** `json.dump`，对 `[]` 零防护。

实测（假 HOME，v1 预置 3 条）：
```python
ms._drawers=[]; ms._primary_ids=set(); ms._save_drawers()
→ 文件从 3 条被清成 0 条
```
⇒ **任何**一次"内存以为自己是空库"的写入路径，都能把非空存储清成 0 条。
这是 v1 变成 `[]` 在 runtime 侧的**可达性来源**——不需要专门代码，走既有 save 路径即可。
