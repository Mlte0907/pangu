## 二、已知问题与风险（证据驱动）

### 2.1 反复出现的缺陷模式

从维护日志中提取的**高频问题家族**：

| 模式 | 出现次数 | 典型表现 | 根因 |
| --- | --- | --- | --- |
| **计量对象错位** | 6 次 | 把缓存命中当真实搜索、把单次实测当稳态 | 测量方法不对，结论方向相反 |
| **静默降级** | 3 次 | 嵌入器坏→FTS 兜底→结果变差无人知 | 异常吞掉，无日志无标志 |
| **文档腐烂** | 2 次 | AGENTS.md 14KB 稀释注意力 | 自动注入的文件无预算约束 |
| **CI 覆盖缺口** | 2 次 | 新增测试文件默认不被跑到 | 手写清单 vs 实际文件不同步 |

### 2.2 当前风险项

| 风险 | 影响 | 证据 |
| --- | --- | --- |
| **LLM 平台侧不稳定** | V4.1 首次 88-121s，GLM 全挂 | 2026-09-27 实测 4 次 |
| **全量测试 10 分钟** | 迭代反馈慢 | 09-27 实测 600s |

## 三、迭代规划

### Phase 1：稳定性加固（1-2 周）

**目标**：消除静默降级，建立可观测性。

| 任务 | 优先级 | 验收标准 | 依据 |
| --- | --- | --- | --- |
| 1.1 LLM 调用链路全量埋点 | P0 | 每次 LLM 调用记录：模型名、延迟、是否降级、token 数 | 当前只有最终结果，无法定位哪一步慢 |
| 1.2 向量/FTS 路径分开度量 | P0 | 搜索响应里返回 `vector_ms` / `fts_ms` / `degraded` | 09-26 修复后 `degraded` 只在内部，API 没暴露 |
| 1.3 模型健康度检查 | P1 | 服务启动时探测所有候选模型，不可用的自动跳过 | V4.1 首次 121s，GLM 全挂，目前要试了才知道 |
| 1.4 云端部署 git 化 | P1 | 云端用 git clone + pull 替代 scp | 当前无版本追踪 |

### Phase 1.5：LLM 接入效果验证（1 周）

**目标**：验证 LLM 在已有模块中的实际效果，建立 token 使用量可观测性。

**当前 LLM 使用现状**（基于代码实测）：

| 模块 | 调用频率 | 用途 | 实测效果 |
| --- | --- | --- | --- |
| `_crystallize_impl` | 12h 一次 | 知识结晶（记忆→知识条目） | ✅ 已验证，产出正常 |
| `compression.py` | 24h 一次 | 旧记忆关键点提取 | ✅ 已验证，压缩正常 |
| `judge.py` | Agent 任务后 | 记忆价值 A/B/C 分类 | ✅ 已验证，判断合理 |
| `enhanced_evaluation.py` | 按需 | 矛盾检测（6 种裁决） | ✅ 已验证，检测准确 |
| `distill_enhanced.py` | 按需 | 知识蒸馏（结构化卡片） | ✅ 已验证，蒸馏正常 |
| `retrievability.py` | 24h 一次 | 可检索性体检 | ✅ 已验证，报告正常 |

**接入后的预期效果**：

| 预期 | 验证方法 | 成功标准 |
| --- | --- | --- |
| 知识结晶产出率提升 | 对比接入前后结晶条目数量 | 结晶跳过率从 >80% 降到 <50% |
| 旧记忆压缩质量 | 人工抽查压缩后的关键点 | 关键点保留核心信息，无幻觉 |
| 记忆价值判断准确率 | 人工标注 10 条记忆，对比 judge 判断 | 准确率 >70% |
| 矛盾检测召回率 | 人工构造 5 组矛盾，检测是否命中 | 召回率 >60% |
| token 使用量可观测 | 仪表盘显示当日 token 使用量 | 实时更新，数据准确 |

**接入后的风险与对策**：

| 风险 | 对策 |
| --- | --- |
| token 成本超预期 | 按日统计 token 使用量，设置告警阈值 |
| LLM 延迟影响自主任务 | 异步执行 + 超时降级到规则式 |
| 模型不稳定（如 V4.1 首次 121s） | 按偏好序自动降级到下一个模型 |
| LLM 幻觉（输出不可靠） | JSON 模式 + 规则式兜底 + 人工抽检 |

| 任务 | 优先级 | 验收标准 | 依据 |
| --- | --- | --- | --- |
| 1.5.1 LLM 按日 token 统计 | P0 | 仪表盘显示当日 LLM token 使用量 | 当前只有累计值，无法按日观测 |
| 1.5.2 LLM 调用效果度量 | P1 | 每次调用记录产出是否可用 | 当前无效果追踪 |

## 四、执行原则

### 4.1 铁律（从维护日志提炼）

1. **先测量再优化** — 不基于单次实测下结论（V4.1 事件教训）
2. **改代码和改测试是一个部署单元** — 云端 gap 事件教训
3. **静默降级 = 事故** — 必须有日志 + 标志（09-26 教训）
4. **文档有预算** — AGENTS.md ≤ 4KB，细节进 MAINTAINERS.md
5. **CI 覆盖不能靠手写清单** — 用目录扫描（09-26 教训）

### 4.2 验收流程

```
改代码 → 单元测试 → 全量测试 → 云端部署 → 线上验证 → 维护日志
```

每一步都要有**可引用的证据**（命令输出 / 测试结果 / 日志截图）。
